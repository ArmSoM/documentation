## 1. 简介

开发板从上电到进入桌面，需要完成内存初始化、加载引导程序、启动内核、挂载根文件系统和启动服务等步骤。了解各阶段的执行流程与依赖关系，有助于定位启动故障、检查相关配置并选择合适的恢复方式。

本文以 ArmSoM 的 Rockchip 平台为主，结合 RK3576、RK3588 系列及 `armsom-sdk` 的 Debian 12、Ubuntu 22.04 镜像说明。两种发行版使用的引导程序和内核可以来自同一套 SDK，主要区别在根文件系统中的软件包与服务；GNOME、XFCE 或 Server 则影响进入用户空间后的运行环境。

:::info 阅读范围
启动原理可用于理解其他 Rockchip 板型，但引导组件、分区布局和启动优先级应以对应板卡、SDK 配置及镜像为准。本文的 `/boot/uEnv` 示例针对 ArmSoM SDK 的相关镜像，Armbian、第三方镜像或 Android 可能采用其他配置方式。
:::

## 2. 系统启动流程

### 2.1 启动阶段与组件职责

![Rockchip Arm64 Linux 启动流程：BootROM、DDR 与早期加载器、TF-A、U-Boot、内核、用户空间](/img/general-tutorial/rockchip-boot-flow.svg)

<div className="armsom-image-caption">典型 Arm64 启动流程，具体组件由板型与 SDK 配置决定</div>

| 阶段 | 主要工作 | 检查要点 |
| --- | --- | --- |
| BootROM | 芯片内部固化的代码，上电后寻找并加载早期引导程序 | 启动介质、引导数据是否有效；此阶段通常没有可见串口日志 |
| DDR 初始化与早期加载器 | 初始化内存，由 SPL 或 miniloader 等加载后续固件 | DDR 参数、内存容量、存储读取与镜像校验 |
| TF-A / 安全固件 | Arm64 平台常见的 BL31 提供安全监控及运行时服务；OP-TEE 可选 | `BL31`、`OP-TEE` 等初始化输出 |
| U-Boot | 初始化启动所需外设，读取启动配置，加载内核、设备树和可选的 initramfs | 启动设备、文件路径、设备树与内核参数 |
| Linux 内核 | 初始化驱动，访问存储并进入根文件系统；可由 initramfs 协助完成 | `Linux version`、驱动日志、根分区挂载结果 |
| 用户空间 | Debian / Ubuntu 通常由 systemd 启动网络、登录、桌面及应用服务 | 登录提示、失败服务、桌面是否启动 |

设备树（DTB）描述板卡上的硬件连接，内核据此配置和匹配驱动。initramfs 是可选的早期用户空间，用于在进入正式根文件系统前加载模块或完成挂载准备；它与保存系统软件和用户文件的 rootfs 不同。

### 2.2 SPL、miniloader 与 rkbin

早期加载器常见两类方案：**DDR 初始化程序配合 U-Boot SPL**，或 **DDR 初始化程序配合 Rockchip miniloader**。部分平台使用 U-Boot TPL 初始化内存，另一些平台使用 Rockchip 提供的 DDR 二进制；采用 SPL 并不意味着所有早期组件都有对应的开源实现。具体组合见 [U-Boot 的 Rockchip 平台说明](https://docs.u-boot.org/en/latest/board/rockchip/rockchip.html)。

[rkbin](https://github.com/rockchip-linux/rkbin) 是 Rockchip 的启动固件与工具仓库，包含 DDR、SPL、USB 下载组件、BL31、OP-TEE 等文件。它是 SDK 的组成部分，不是 Debian 或 Ubuntu 系统镜像。

:::tip 如何判断是否已经进入 Linux
出现 `Starting kernel ...` 表示 U-Boot 准备把控制权交给内核；随后出现 `Linux version` 才能确认内核已开始输出。能通过串口或 SSH 登录，说明系统已进入用户空间，HDMI 黑屏需要进一步检查显示配置和桌面服务。
:::

## 3. SDK 中的启动文件

### 3.1 构建产物与分区的关系

SDK 构建完成后，通常通过 `rockdev/` 查看打包文件，部分版本实际链接到 `output/firmware/`。以下结合 ArmSoM SDK 的常见输出说明，各文件不一定在所有方案中同时出现。

| 文件 | 作用 | 与启动的关系 |
| --- | --- | --- |
| `MiniLoaderAll.bin` 或带芯片型号的 `*_loader_*.bin` | 供烧录工具使用的 Loader 包 | 用于初始化内存、建立下载能力等，具体组成由 SDK 决定 |
| `uboot.img` | U-Boot 阶段的固件 | 部分 SDK 使用 FIT 打包，可同时包含 U-Boot、安全固件等组件 |
| `trust.img` | 独立的安全固件镜像 | 某些方案使用；安全固件已包含在 FIT 中时，不一定单独生成 |
| `boot.img` / `extboot.img` | 启动分区镜像 | ArmSoM SDK 的相关配置中，`boot.img` 链接到内核生成的 `extboot.img`，承载启动脚本、内核、设备树等 |
| `rootfs.img` | 根文件系统镜像 | 包含 Debian / Ubuntu 的系统程序、库和服务 |
| `parameter.txt` | 分区布局配置 | 描述分区名称、大小和位置，须与板型及打包配置匹配 |
| `update.img` | 整合后的升级包 | 将 Loader、分区配置及镜像等交给烧录工具处理，CPU 不会直接执行整个升级包 |

在其他 U-Boot 构建方案中，还可能看到 `idbloader.img`、`u-boot.itb` 或 `u-boot-rockchip.bin`。这些名称对应不同的打包方式，不能直接替换 SDK 中的同类文件。构建与打包步骤见 [ArmSoM SDK 使用指南](../build_and_deploy/armsom-sdk.md)。

:::warning 不要套用固定烧录偏移
网上示例中的扇区地址不一定适用于当前镜像。烧录位置应依据对应板型的分区表、打包配置和工具说明；也不能仅凭 `uboot.img` 这个名字判断是否需要另一个 `trust.img`。
:::

### 3.2 系统中的 `/boot` 目录

采用 ArmSoM SDK 启动脚本的镜像，通常可以在 `/boot` 下找到以下内容：

| 路径或文件 | 用途 |
| --- | --- |
| `boot.scr` | U-Boot 执行的启动脚本，负责读取配置并加载内核等文件 |
| `uEnv/uEnv.txt` | 启动配置入口，可通过软链接指向对应板型的配置 |
| `rk-kernel.dtb` | 主设备树入口，相关镜像通过软链接选择板型 DTB |
| `dtb/`、`dtb/overlay/` | 主设备树及设备树插件 |
| 内核与 initrd 文件 | 由启动脚本和配置选择，具体名称随镜像与内核版本变化 |

U-Boot 读取的是启动分区内的路径，而 Linux 可能把这个分区挂载到 `/boot`。因此，串口中的 `/uEnv/uEnv.txt` 与登录系统后看到的 `/boot/uEnv/uEnv.txt` 可以是同一个文件。

设备树插件的配置方法见 [overlay 配置](<../Getting Started/14.overlay.md>)。更换内核时，还要匹配设备树、内核模块和启动配置，更新步骤参考 [ArmSoM SDK 使用指南](../build_and_deploy/armsom-sdk.md) 的“更新内核”章节。

## 4. 启动介质与下载模式

### 4.1 启动介质与系统加载路径

启动配置需要区分 **早期引导程序的加载介质** 与 **内核、根文件系统的存储位置**。这些组件可以部署在同一介质，也可以根据启动固件的支持情况分布在不同设备上。

| 介质或方式 | 常见用途 | 前置条件 |
| --- | --- | --- |
| eMMC / microSD | 存放引导程序、启动分区和根文件系统 | 镜像适配板型，介质可读，启动配置正确 |
| SPI Flash | 保存早期引导程序和 U-Boot，再加载其他设备上的系统 | 板卡具备相应硬件，并提供匹配的 SPI 固件 |
| NVMe / USB 存储 | 保存根文件系统，也可在支持的方案中存放内核 | 通常需要先从 SPI、eMMC 或 SD 等介质运行引导程序，再由后续阶段访问该设备 |
| 网络启动 | 例如通过 TFTP 加载内核、通过 NFS 提供根文件系统 | 已有可运行的引导程序，并配置网络、内核和根文件系统 |

:::info 分阶段的介质选择与优先级
BootROM 负责选择早期引导介质，SPL 和 U-Boot 根据各自配置加载后续镜像。各阶段的介质选择与优先级由芯片、板级配置和启动固件共同决定。根分区位于 NVMe 时，仍需结合早期启动日志确认引导程序的加载介质。
:::

### 4.2 正常启动、Loader 与 Maskrom

| 模式 | 所处状态 | 主要用途 |
| --- | --- | --- |
| 正常启动 | 按配置加载内核和系统 | 运行 Debian、Ubuntu 或其他系统 |
| Loader 下载模式 | 下载程序已运行，可与电脑的烧录工具通信 | 固件升级、分区写入等操作 |
| Maskrom 模式 | 由芯片 BootROM 提供的 USB 下载入口 | 空白介质、早期引导损坏或主动进入下载模式时使用；通常需要先加载匹配的 Loader |

进入方式请参考对应产品的按键和 USB OTG 接口说明，再按 [系统镜像烧录](<../Getting Started/2.flash-img.md>) 操作。**Recovery 按键、Loader 下载模式和 Android Recovery 系统不是同一个概念**，应以工具识别结果及板卡说明为准。

## 5. 在板端查看启动状态

以下命令在已经登录的 Debian / Ubuntu 终端执行。它们用于读取状态和日志，无需先安装额外的开发工具。

### 5.1 确认板型、内核与根分区

```bash
tr '\0' '\n' < /proc/device-tree/model
uname -r
cat /etc/os-release
cat /proc/cmdline
```

依次查看当前设备树中的板型、正在运行的内核、发行版和内核启动参数。`/proc/cmdline` 中的 `root=` 常用于指定根分区，`console=` 指定内核日志输出终端。

```bash
findmnt -o SOURCE,FSTYPE,TARGET /
findmnt -T /boot
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,PARTUUID
```

`findmnt` 显示当前实际挂载的设备；`lsblk` 用于对应磁盘与分区。`/boot` 可能是独立分区，也可能是根文件系统中的目录。不要把某个固定的 `mmcblk` 编号当成所有镜像通用的 eMMC 或 SD 卡标识。

### 5.2 查看启动配置与设备树

先查看 `/boot`，再读取存在的配置：

```bash
ls -l /boot
if [ -f /boot/uEnv/uEnv.txt ]; then
    ls -l /boot/uEnv/uEnv.txt
    cat /boot/uEnv/uEnv.txt
fi
if [ -e /boot/rk-kernel.dtb ]; then
    ls -l /boot/rk-kernel.dtb
fi
```

关注配置中选择的内核、initrd、启动参数和 overlay，以及软链接是否指向正确板型。磁盘上的配置影响后续启动；判断当前运行状态仍应结合 `/proc/cmdline`、设备树与启动日志。

:::tip 没有 uEnv 文件时
部分镜像采用 `extlinux.conf` 或其他启动机制。先结合 `/boot` 内容和 U-Boot 日志确认加载路径，不要直接从另一套镜像复制 `uEnv.txt`。
:::

### 5.3 查看服务和启动耗时

```bash
systemctl --failed --no-pager
sudo journalctl -b -p warning --no-pager
systemd-analyze time
systemd-analyze critical-chain
```

前两条命令查看本次启动的失败服务和警告日志，后两条用于分析 systemd 记录的启动耗时与关键依赖链。若提示启动尚未完成，应结合失败服务和日志继续检查。

:::info 启动耗时的边界
`systemd-analyze` 不一定包含 BootROM、DDR 初始化和 U-Boot 的时间，也不等于从按下电源到桌面可操作的完整耗时。需要测量全过程时，应另行记录上电和目标界面就绪的时间。计时含义见 [systemd 官方说明](https://www.freedesktop.org/software/systemd/man/latest/systemd-analyze.html)。
:::

## 6. 按启动阶段排查问题

### 6.1 启动故障的阶段定位

排查时，先按对应产品文档连接调试串口，并从上电前开始保存完整日志。串口接线、电平和波特率以板型说明为准。

| 现象 | 优先检查 |
| --- | --- |
| 串口完全无输出 | 电源、调试串口接线、波特率及串口设备；不能仅凭无输出判定 BootROM 损坏 |
| 停在 DDR 初始化或 SPL | 板型与 Loader 是否匹配、供电是否稳定、后续镜像能否读取 |
| 已进入 U-Boot，但找不到内核或 DTB | 启动分区、脚本路径、文件是否存在、软链接目标是否有效 |
| 停在 `Starting kernel ...` 后无输出 | `console=` 配置、内核与 DTB 的匹配情况；也可能只是日志输出终端改变 |
| `Unable to mount root fs` 或持续等待根设备 | `root=` 参数、分区标识、存储驱动、文件系统支持及必要的 initramfs |
| 已能登录，但桌面未显示 | 是否为 Server 镜像、显示连接、图形驱动与桌面服务 |
| 进入系统较慢或出现失败服务 | 本次启动日志与服务依赖；联网、挂载或应用服务是否长时间等待 |

以下节选自 CM5（RK3576）的串口启动记录，省略了中间输出：

```text
U-Boot SPL board init
Trying to boot from MMC2
MMC: no card present
...
Trying to boot from MMC1
...
Bootdev(atags): mmc 0
...
Found U-Boot script /boot.scr
...
Starting kernel ...
...
[    2.957186] VFS: Mounted root (ext4 filesystem) on device 179:3.
```

这段日志中，一次介质探测失败后，后续介质仍完成了启动。应结合后续输出判断结果，不能仅看到 `no card present` 就认定启动失败；SPL、U-Boot 与 Linux 中的设备编号也不应直接等同。

### 6.2 保存排查信息

系统能登录时，可以把本次启动的日志保存到 `~/boot-logs`：

```bash
mkdir -p ~/boot-logs
sudo journalctl -b -k --no-pager > ~/boot-logs/kernel.log
sudo journalctl -b --no-pager > ~/boot-logs/system.log
```

`kernel.log` 保存内核日志，`system.log` 保存系统日志。这两个文件不包含完整的 BootROM、DDR 和 U-Boot 串口输出，早期阶段仍需由电脑端的串口工具记录。

反馈问题时，附上板型、镜像文件名、供电和启动介质、最后一次改动，以及完整串口日志。基础上电和登录步骤可参考 [启动系统与系统登录](<../Getting Started/4.board-startup.md>)。
